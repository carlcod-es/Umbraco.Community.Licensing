## Context

See proposal.md (Why). What the sample builds on:

- **Library public API.** `LicenseEvaluator(productId, TrustedSigningKeys, TimeProvider?)` is
  immutable and thread-safe; `Evaluate(string?)` never throws. `LicenseResult` gives `State`,
  `IsLicensed`, `License` (verified expiry and features, also for `Expired`), `ClaimedProduct`,
  `ClaimedKeyIdentifier`, `HasSwitch`, `GetNumber`, `GetText`. `LicenseIssuer`,
  `SigningKeyPair`, `SigningPrivateKey` and `SigningPublicKey` are public, so demo keys can be
  issued without internals. The library grants `InternalsVisibleTo` to its own tests only.
- **`NotSupported`** is produced only by a key with content from a newer format (library
  example 11). The public issuer cannot write one; the library tests use an internal seam.
- **Build.** `release.yml` builds, tests and packs all of `Umbraco.Community.Licensing.slnx`;
  CI uses Node 22. The repo pins package versions inline (no central package management) and
  the root `Directory.Build.props` sets `TreatWarningsAsErrors` for every build.
- **Umbraco 17.** The backoffice client needs Node 24.13 or later. Umbraco's transitive
  packages raise NuGet advisory warnings (NU1901 to NU1904) from time to time. The
  `umbraco-extension` and `umbraco` templates (verified 17.7.1, 2026-10-21) produce a Razor class
  library with a Lit, Vite and TypeScript client, and an SQLite site with unattended install.
  Template defects known from Carl's package scaffold on 17.7 (hey-api peer version, generator
  config, `hey-api.ts` cast) were checked at scaffold: none occurs on 17.8.1.
- **Existing example keys** (ADR-0005): `Nb_sm4Fxh5c` and `MoA_5TxIpJs`, trusted by the
  library's tests only.

## Bar

**Prototype.** The sample is never published and runs only on a developer's machine. Vendors
copy it, though, so the licensing code (everything under `Licensing/` in the package) is held
to the library's standard: every `sample-package` and `sample-demo-site` scenario with
server-side behaviour has an automated test. The backoffice screens, the public page markup and
the demo site's first run are checked by Carl by hand (Test strategy, Observed).

## Goals / Non-Goals

**Goals:** a product that uses only the library's public API the way a vendor would; licensing
logic in plain, testable services, separate from Umbraco plumbing; all user-facing wording
produced on the server so tests cover it; demo-only code in one folder per project, removable
in one step; the library build and release untouched.

**Non-Goals:** submissions storage, email, spam protection, validation beyond required fields;
Umbraco 18; a Marketplace or NuGet listing; a package template for vendors; automated browser
tests; localisation of the sample's wording.

### Solution, build isolation and CI (ADR-0026)

- **Own solution** `samples/Acme.ContactForm.slnx`. The root solution and `release.yml` do not
  change, so the release never restores Umbraco, never needs Node 24 and can never pack the
  sample. Every sample project sets `IsPackable=false`.
- **`samples/Directory.Build.props`** imports the root props (so .NET 10, nullable, warnings as
  errors still apply) and adds `WarningsNotAsErrors` NU1901 to NU1904, so an Umbraco advisory
  cannot break the build overnight. No other relaxation.
- **Library by project reference** (`..\..\src\Umbraco.Community.Licensing\...csproj`), so a
  library change that breaks a real product's usage fails the sample at once.
- **CI**: new `.github/workflows/sample.yml` on pull requests and pushes to `main` with paths
  `samples/**`, `src/Umbraco.Community.Licensing/**`, `global.json`, `Directory.Build.props`
  and the workflow itself. Ubuntu, Node 24, `npm ci` and `npm run build` in the client,
  `node --test samples/run-demo.test.mjs`, then `dotnet build` and `dotnet test` of the sample
  solution in Release. Actions pinned by commit as in `ci.yml`. The steps are run locally first;
  Carl then pushes and the run on GitHub Actions is the final check.
- **Generated client not checked against the live API** (accepted, Carl 2026-11-13): generating
  needs a running site, so CI does not regenerate `src/api/**` and compare. The server contract
  is covered by the C# controller tests and the export check (task 6.3); the screens by the
  observed checks in section 10.
- **Versions** pinned inline and exactly, as the rest of the repo does; no central package
  management for one solution.

### The licensing core (copy this)

All licensing logic sits in `Licensing/` as plain classes with no Umbraco types, so it is
unit-tested without a site:

- **`ContactFormProduct`**: product ID `acme.contact-form`, feature names, and the demo public
  key as a constant trusted line, as a vendor compiles its own public key into its product.
  Builds the one `LicenseEvaluator`, registered as a singleton.
- **`ILicenseKeySource`**: `(string? Key, string SourceName)`. The default reads
  `ContactFormOptions.LicenseKey` through `IOptionsMonitor`, so a settings-file change is picked
  up without restart. The demo source (below) wraps it.
- **`ContactFormLicensing.Check(string host)`** → `LicenseSnapshot`: reads the key source,
  calls `Evaluate`, and derives: uploads granted; monthly limit and usage; domain covered for
  `host`; expiring soon (expiry minus now ≤ 30 days, using `ContactFormProduct.Clock`, the clock
  the evaluator was built with, so the two cannot differ); and
  the key source name. Called on every render, submission, dashboard and banner request
  (spec: Evaluated when used). One evaluation is microseconds (PDR-0022), so no cache.
- **`FirstActions`**: a switch over `LicenseState` with no default branch, giving the
  dashboard's action text; the compiler and a test over `Enum.GetValues<LicenseState>()` both
  catch a new state. Wording follows `docs/how-it-works.md#states`.
- **Projections**: `AdminLicenseStatus` (dashboard data) and `EditorLicenseBanner` (case,
  message, optional expiry date, optional used/limit). Built from the snapshot; neither type has
  a field that could hold the key string, and the editor type has no identifier, state or
  product field (spec: Editor sees no license details). Tests serialise each for every demo key
  and assert the key string and, for the editor, the identifier and state names are absent.
- **Banner wording** is server-side, one message per case (not valid; expiring soon; over
  limit; domain not covered), several cases joined, each ending "Contact your administrator."
- **`LicenseStateLog`**: given the snapshot by `Check`, compares its condition (state, and
  expiring soon when `Valid`) with the last logged one under a lock and writes one `ILogger`
  message on change: Information for `Valid`, Warning for `Valid` and expiring soon (with the
  expiry date), Error for any other state (PDR-0071). It names the identifier or claimed identifier
  (`LicenseResult.ToString()` already prints only the identifier).
- **Domain check**: `licensed-domains` split on `,`, trimmed, compared ordinal-ignore-case with
  `HostString.Host` (port dropped). Empty entries are ignored. The check runs only for a `Valid`
  license; `AdminDomainStatus.Checked` says whether it ran, and `Covered` means something only
  when it did.

### Public form

- A view component renders the form from a view model with `ShowUploads` only. The Razor view
  has no other input from licensing, so nothing about licensing can reach the page (spec: No
  licensing in public output). A test builds the view model for every demo key.
- A surface controller posts the form, checks required fields, and records the submission
  whatever the state. A file is read for name and length only when `ShowUploads` is true for
  that request; otherwise it is ignored. A file over 1 MB is not read and the submission is kept
  without it; the request body itself is limited only by the server's default (Umbraco does not
  apply a per-action request size limit).
- The thank-you response is the same in every state.

### Submissions

`InMemorySubmissionStore`, a singleton: a list under a lock, and a count for the current UTC
month from the real `TimeProvider` (the demo clock does not affect the count). Restart clears
it. Behind `ISubmissionStore` so a vendor sees where real storage would plug in.

### Backoffice API and client (ADR-0027)

- **Management API controllers** in the package, Umbraco 17 style (`[BackOfficeRoute]`,
  `[MapToApi("acme-contact-form")]`, `ControllerBase`), with their own OpenAPI document:

| Endpoint | Policy | Returns |
|---|---|---|
| `GET license/status` | Settings section access | `AdminLicenseStatus` only; no demo field (a demo selection shows in `KeySourceName`) |
| `GET submissions` | Content section access | Submissions this month and `EditorLicenseBanner` |
| `GET demo/entries` | Settings section access; 404 when demo off | `DemoEntriesResponse`: `Entries` ("Configured key" first; each `DemoEntryItem` with name, description, `HasDemoDate`, `DemoDate` as `yyyy-MM-ddTHH:mm:ssZ`) and `Selected` (entry name, or "Configured key") |
| `POST demo/select` | Settings section access; 404 when demo off | Body `{ "entry": "<name>" }`; "configured" or "Configured key" returns to the configured key; 204; an unknown entry gets 400 (ProblemDetails) and leaves the selection unchanged |

- **Client**: the 17 template's Lit, Vite and TypeScript setup and its generated hey-api client
  (regenerated with `npm run generate-client` against a running site; generated files
  committed, as the template does). Two dashboards in `umbraco-package.json`/manifests: the
  licensing dashboard with the Settings section condition, the submissions dashboard with the
  Content section condition. The picker element lives in `src/demo/` and is shown only when
  `demo/entries` answers. All wording comes from the server; the client lays it out with UUI
  elements.
- **Add-on points on the licensing dashboard**: an `<umb-extension-slot>` for the custom
  extension type `acmeContactFormLicensePanel`, where the picker renders, and the `window`
  event `acme-contact-form-license-changed`, which makes the dashboard fetch `license/status`
  again. The picker registers its own manifest and dispatches the event; the dashboard imports
  nothing from `src/demo/`.
- Template defects from the scaffold notes (hey-api peer minimum, 17 generator config, 17
  `hey-api.ts` cast) were checked in section 2; none occurs on 17.8.1, so none is patched.

### Demo keys, picker and demo clock (ADR-0028)

- **Demo signing pairs** created once with the library's public `SigningKeyPair` by an explicit
  generator test and committed in `samples/demo-signing-keys/` (`demo.pem`, `demo.public.txt`,
  `untrusted.pem`, `untrusted.public.txt`, `README.md`), each file starting with the
  "public, demo-only, never trust" warning. Not in the package project, so its build output
  never holds a private key.
- **`Demo/demo-keys.json`**, embedded in the package: per entry `name`, `description`, `key`
  (null for No key), `demoDate` (only Valid: expiring soon), and the expected `state`,
  `product`, `productVerified` (false when the product is only claimed), `expires` and features,
  which the tests assert.
- **Generator**: an explicit xUnit test (`-explicit only -method "*DemoKeyGenerator*"`), as
  ADR-0005, reading the PEMs, issuing with `LicenseIssuer` and a fixed issue clock, printing
  the JSON and writing it to `Demo/demo-keys.json`. Edited key: the full-plan key with one character of its signature part replaced by a
  fixed different character; the test asserts `NotVerified`. Damaged key: a fixed string that is
  not a key. Fixed expiries: small plan 2099-12-31T23:59:59Z; expiring soon
  2030-01-31T23:59:59Z with demo date 2030-01-17T12:00:00Z (14 days); expired
  2026-01-31T23:59:59Z.
- **Demo key tests** (always run): every entry, at its demo date, yields its documented state,
  claimed or verified product, expiry and features; the demo key ID differs from `Nb_sm4Fxh5c`
  and `MoA_5TxIpJs`; the untrusted pair's ID is not in the product's trusted set.
- **Picker**: `DemoKeySelection` singleton holding the chosen entry or none. `DemoKeySource`
  decorates the configured `ILicenseKeySource` when `ContactForm:Demo:Enabled` is true; it
  returns the chosen entry's key and the source name `Demo selection: <entry>`. Nothing writes
  configuration.
- **Demo clock**: `DemoClock : TimeProvider` returns the chosen entry's demo date when it has
  one and the system clock otherwise; given to the evaluator and the expiring-soon check only.
  It is never registered as the container's `TimeProvider`, so the submission count keeps the
  real clock.
- **Off by default**: `ContactForm:Demo:Enabled` defaults to false in `ContactFormOptions`; the
  demo site's committed `appsettings.json` sets it true. With it false, the demo services are
  not registered and the demo endpoints answer 404.
- **Removed in one step** (PDR-0069): a composer in `Demo/`, ordered after the package's
  composer, registers the demo services, and no file outside `Demo/` (and the client's
  `src/demo/`) refers to them. The picker reads the selection and demo date from
  `demo/entries`, so `license/status` carries no demo field. On the client, the picker is
  loaded through its own manifest entry in `src/demo/`, never imported by the dashboard, so
  deleting `src/demo/` leaves the client building: `bundle.manifests.ts` names
  `./demo/manifest.ts` only through `import.meta.glob`, which matches nothing once the folder is
  gone.

## Risks / Trade-offs

- [Umbraco and npm packages bring advisories and churn] → sample-only solution, exact pins,
  NU1901 to NU1904 not errors, nothing reaches the release.
- [A committed demo private key is mistaken for a real one, or trusted by a copied product] →
  warning header in every file, README section, a key ID distinct from the library examples,
  the private keys outside the package project.
- [A beta format change turns every demo key `NotSupported`] → demo key tests fail in CI with
  the entry name; one regeneration command.
- [The demo picker is copied into a real product] → `Demo/` and `src/demo/` folders, off by
  default, Settings only, README "delete when copying".
- [The domain check uses the backoffice host for the dashboard, which can differ from the
  public host] → acceptable for a sample; the dashboard names the host it checked.
- [Template defects or a new 17.x template release break scaffolding] → patches listed in the
  README; the exact versions recorded in ADR-0026 at task 2.1.
- [Node 24 for the sample, Node 22 elsewhere in CI] → separate workflow; `docs/development.md`
  says which needs which.
- [In-memory submissions look like a pattern] → `ISubmissionStore` seam and README note.
