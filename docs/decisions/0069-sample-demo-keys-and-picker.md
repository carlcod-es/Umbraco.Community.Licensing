# PDR-0069: Sample demo keys and the demo key picker

- Status: Decided
- Date: 2026-11-13
- Source: `add-sample-package` design.md Q3, Q7, Q11, Q12, Q13
- Personas: vendor and implementor (every state can be seen in a minute, with no tool or key
  setup). Site owner (primary): demo keys are signed by a key no real product trusts.
  Backoffice editor: the picker is not available to them. Site visitor: unaffected.

## Context

To show what the product does in each state, the demo site needs keys for each state and a way
to switch between them. The library issues keys only with a private key, so the demo needs a
signing key of its own.

## Decision

- **Demo signing keys committed.** One demo pair, trusted only by the sample product, and one
  untrusted pair for the untrusted-signer key. Every file holding a demo private key says it is
  public, for demonstration only, and never to be trusted by a real product. The demo keys are
  not the library's example keys.
- **Ten demo keys**: Valid full plan, small plan, another domain and expiring soon; Expired; No
  key; Damaged key; Another product's key; Untrusted signer; Edited key. `NotSupported` is not
  demonstrated: it needs a key from a newer format, which cannot be issued today, and its first
  action is still shown by the product's tests.
- **Checked on every change and regenerated by one command** when the beta key format changes.
- **The demo site starts on the Valid full-plan key** through the normal key setting.
- **Demo key picker** on the administrator dashboard: "Configured key" and the ten entries.
  Choosing one applies at once to the dashboard, the editor banner and the public form, until
  another is chosen or the site restarts. It never changes configuration, and the dashboard
  says when it is showing a demo selection.
- **Settings users only, demo setting only.** The picker exists only when the site turns the
  demo setting on (off unless set) and only for users with Settings access.
- **Demo date.** The "expiring soon" entry carries a demo date the product treats as now while
  it is chosen; the dashboard shows it.

## Reasons

- Committed keys make the sample work from a clone with no setup, and the files are a worked
  example in their own right.
- One key per state the issuer can produce covers every first action a vendor writes.
- Forging a `NotSupported` key would copy the library's internal format into the sample.
- A picker shows every state in one session; editing configuration and restarting for each is
  slow.
- Never writing configuration and resetting on restart means the demo cannot leave a site in a
  surprising state.
- An "expiring soon" key from a fixed date would stop being "soon" within days; a demo date
  keeps it true.

## Rejected options

| Option | Why rejected |
|---|---|
| Keys generated on first run | More moving parts; nothing to read in the repo |
| Bring your own keys with the vendor tool | The sample would not work until the vendor sets up the tool |
| Editing configuration per state | Slow; Carl chose the picker (2026-11-13) |
| Launch profiles per state | Restart per state; harder to compare states |
| Picker that writes the settings file | Leaves the site changed after the demo |
| Picker on by default | A copied product would ship a way to swap its key |

## Consequences

- The demo private keys are public. Any product trusting the demo key would accept keys from
  anyone.
- The picker is demo code, kept apart so it is removed in one step when copying.
