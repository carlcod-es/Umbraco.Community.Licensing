# Acme Contact Form sample

This folder holds a demo site for the fictional Acme Contact Form product. It is never published.

## Prerequisites

- .NET 10 SDK
- Node 24.13 or newer

## First run

From the repo root, run:

```
node samples/run-demo.mjs
```

The command does this:

- Runs `npm ci` in `Acme.ContactForm/Client` if `node_modules` is missing.
- Runs `npm run build` if the client bundle is missing or older than the client sources.
- Runs `dotnet run --project samples/Acme.ContactForm.Site`.

When the site is up, browse to <http://localhost:15329> and log in at <http://localhost:15329/umbraco> with the demo administrator:

- Email: `demo@acme.example`
- Password: `Acme-Demo-Only-1`

This login is public and is for the local demo only. Change it in any site you build from this sample.

The first start installs Umbraco, so it takes a little longer.

## Notes

- `Acme.ContactForm.Site/appsettings.json` holds demo values generated by the Umbraco template (`Umbraco:CMS:Imaging:HMACSecretKey` and `Umbraco:CMS:Global:Id`). Never reuse them in a real site.
- `Acme.ContactForm.Site/appsettings.Local.json` is an optional personal override, for example your own administrator login. It is gitignored and not a required step. It is only loaded in Debug builds (`#if DEBUG` in the site's `Program.cs`). `dotnet run` builds Debug by default, so the start command above picks it up. Do not pass `-c Release`.

## Demo keys

The demo keys are ten ready-made license keys, one for each situation the product has to handle. The demo site's picker offers them, and the tests check them on every change.

| Entry | What it shows |
|---|---|
| Valid: full plan | `Valid`, perpetual, with uploads, 1000 submissions a month and `localhost`. |
| Valid: small plan | `Valid`, expires on 2099-12-31, with no uploads, 3 submissions a month and `localhost`. |
| Valid: another domain | `Valid`, for `www.example.com` only. |
| Valid: expiring soon | `Valid`, 14 days from expiry at its demo date (2030-01-17), so the warning shows. |
| Expired | `Expired`, with the full plan's features. |
| No key | `Missing`: no key is configured. |
| Damaged key | `Unreadable`: the text is not a key. |
| Another product's key | `WrongProduct`: a genuine key for `acme.commerce`. |
| Untrusted signer | `SigningKeyNotRecognised`: signed by a key the product does not trust. |
| Edited key | `NotVerified`: the full-plan key with one character of its signature changed. |

`NotSupported` is not demonstrated. It needs a key in a newer format than this library writes, and only the library's internal test seam can produce one. The sample uses the public API only. The product's own tests still cover its first action.

The keys live in `Acme.ContactForm/Demo/demo-keys.json`, which is embedded in the package project. Each entry holds its key and the state, product, expiry and features it must show. `Acme.ContactForm.Tests` evaluates every entry and fails, naming the entry, when one reads differently.

The signing pairs are public and demo-only. See [demo-signing-keys/README.md](demo-signing-keys/README.md). Never trust them in a real product.

To issue the whole set again, for example after a change to the key format, run this from the repo root:

```
dotnet run --project samples/Acme.ContactForm.Tests -- -explicit only -method "*DemoKeyGenerator*" -showLiveOutput
```

It prints the new JSON and replaces `Demo/demo-keys.json`. Regenerating replaces every key and identifier. It is not part of the normal test run.
