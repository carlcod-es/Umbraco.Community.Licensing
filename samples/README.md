# Acme Contact Form sample

This folder holds a demo site for the fictional Acme Contact Form product. It is never published.

## Prerequisites

- .NET 10 SDK
- Node 24.13 or newer

## Trust the development certificate

The demo site is served over HTTPS at `https://localhost:44365`. The one setup step is to trust the local development certificate, once per machine:

```
dotnet dev-certs https --trust
```

On Windows and macOS this prompts you to confirm. `dotnet dev-certs https --check --trust` tells you whether it is already trusted. On Linux the command does not trust the certificate for every browser and tool; follow Microsoft's guidance: [Trust HTTPS certificate on Linux with linux-dev-certs](https://learn.microsoft.com/aspnet/core/security/enforcing-ssl#trust-https-certificate-on-linux-with-linux-dev-certs). Microsoft supports the trust command officially on Ubuntu and Fedora, with manual steps for other distributions.

`run-demo.mjs` runs the check for you. If the certificate is not trusted it prints the command above and starts the site anyway, so the browser will warn until you trust it.

## First run

From the repo root, run:

```
node samples/run-demo.mjs
```

The command does this:

- Runs `npm ci` in `Acme.ContactForm/Client` if `node_modules` is missing.
- Runs `npm run build` if the client bundle is missing or older than the client sources.
- Checks the development certificate with `dotnet dev-certs https --check --trust`; if it is not trusted, prints the trust command and starts anyway.
- Runs `dotnet run --project samples/Acme.ContactForm.Site --launch-profile https`.

When the site is up, browse to <https://localhost:44365> and log in at <https://localhost:44365/umbraco> with the demo administrator:

- Email: `demo@acme.example`
- Password: `Acme-Demo-Only-1`

This login is public and is for the local demo only. Change it in any site you build from this sample.

The first start installs Umbraco, so it takes a little longer. It also seeds two pages.

The plain address `http://localhost:15329` still answers, but only to forward: it redirects (307) to the same path at `https://localhost:44365`.

### Home and Contact

- Home is the site root (`/`). It shows a heading, intro text, an About text and a link to Contact. The About text says what the sample is and starts with a short description of the package and this library.
- Contact (`/contact/`) shows a heading, intro text and the contact form.

Both share one plain layout: a header with the site name and a link to each page, and a footer. The footer shows the editable footer text and, on every page, a fixed link "Umbraco.Community.Licensing on GitHub" to https://github.com/carlcod-es/Umbraco.Community.Licensing (it is in `Views/_Layout.cshtml`, not content). In the back office, under Content, an editor can change:

- the site name and the footer text (the footer starts "Demo site for Acme Contact Form"),
- each page's heading and intro text, and Home's About text,
- each page's name, which is what the navigation links show.

The site is made of these files in `Acme.ContactForm.Site`: `Composers/DemoContentSeeder.cs`, which creates the document types, templates and pages when the site has started (`Composers/DemoContentComposer.cs` registers it); `Views/home.cshtml` and `Views/contact.cshtml`, which the seeder reads as the two templates; and `Views/_ViewStart.cshtml`, `Views/_Layout.cshtml` and `wwwroot/css/site.css`, the layout and stylesheet those views use. A vendor can copy or remove them.

### Data from an earlier version

If you ran an earlier version of the sample, its data in `Acme.ContactForm.Site/umbraco/Data` has no Home and Contact content, or has a Home without the About text. The site logs "The demo data comes from an earlier version of the sample: the 'home' document type has no 'about' (About text). Delete umbraco/Data and start again; nothing was seeded." Stop the site, delete the `Acme.ContactForm.Site/umbraco/Data` folder and start again. Deleting it removes the installed data and any content you changed. The next start installs again and recreates the demo administrator from the committed settings (or from your `appsettings.Local.json`, if you have one).

## Notes

- `Acme.ContactForm.Site/appsettings.json` holds demo values generated by the Umbraco template (`Umbraco:CMS:Imaging:HMACSecretKey` and `Umbraco:CMS:Global:Id`). Never reuse them in a real site.
- `Acme.ContactForm.Site/appsettings.Local.json` is an optional personal override, for example your own administrator login. It is gitignored and not a required step. It is only loaded in Debug builds (`#if DEBUG` in the site's `Program.cs`). `dotnet run` builds Debug by default, so the start command above picks it up. Do not pass `-c Release`. In Debug, a `ContactForm:Demo:Enabled` in this file overrides the `ContactForm__Demo__Enabled` environment variable.

## Demo keys

The demo keys are ten ready-made license keys, one for each situation the product has to handle. The demo site's picker offers them, and the tests check them on every change.

| Entry | What it shows |
|---|---|
| Valid: full plan | `Valid`, perpetual, with uploads, 5 submissions a month and `localhost`. |
| Valid: small plan | `Valid`, expires on 2099-12-31, with no uploads, 3 submissions a month and `localhost`. |
| Valid: another domain | `Valid`, for `www.example.com` only. |
| Valid: expiring soon | `Valid`, 14 days from expiry at its demo date (2030-01-17), so the warning shows. |
| Expired | `Expired`, with the full plan's features. |
| No key | `Missing`: no key is configured. |
| Damaged key | `Unreadable`: the text is not a key. |
| Another product's key | `WrongProduct`: a genuine key for `acme.commerce`. |
| Untrusted signer | `SigningKeyNotRecognised`: signed by a key the product does not trust. |
| Edited key | `NotVerified`: the full-plan key with one character of its signature changed. |

`NotSupported` is not demonstrated. It needs a key in a newer format than this library writes, and only the library's internal test seam can produce one. The sample uses the public API only. The product's own tests still cover its first action.

The keys live in `Acme.ContactForm/Demo/demo-keys.json`, which is embedded in the package project. Each entry holds its key and the state, product, expiry and features it must show. `Acme.ContactForm.Tests` evaluates every entry and fails, naming the entry, when one reads differently.

The signing pairs are public and demo-only. See [demo-signing-keys/README.md](demo-signing-keys/README.md). Never trust them in a real product.

To issue the whole set again, for example after a change to the key format, run this from the repo root:

```
dotnet run --project samples/Acme.ContactForm.Tests -- -explicit only -method "*DemoKeyGenerator*" -showLiveOutput
```

It prints the new JSON and replaces `Demo/demo-keys.json`. Regenerating replaces every key and identifier, including the full-plan key, so update `ContactForm:LicenseKey` in `Acme.ContactForm.Site/appsettings.json` afterwards. It is not part of the normal test run.

## Licensing/: what to copy

A vendor builds the licensing for their own product by copying files from `Acme.ContactForm/Licensing/`:

| File | What it is for |
|---|---|
| `ContactFormProduct.cs` | The product: its ID, its feature names and the public key it trusts, compiled in. Holds the one license evaluator. |
| `ContactFormOptions.cs`, `ILicenseKeySource.cs` | The site owner's `ContactForm` settings and the key source that reads the key on every use, so a changed key needs no restart. |
| `ContactFormLicensing.cs` | The snapshot check. It evaluates the key and answers what the product acts on: state, uploads, monthly limit, domain, days left. |
| `FirstActions.cs` | The first action to tell a site owner for each state. |
| `AdminLicenseStatus.cs`, `EditorLicenseBanner.cs` | The two projections of a snapshot: the full status for an administrator and a short banner for an editor. Neither holds the key. |
| `LicenseStateLog.cs` | One line each time the condition changes (Information when Valid, Warning when expiring soon, Error for any other state), naming the key identifier and never the key. |

The wiring is in `Extensions/` (`AddContactForm()`, which calls `AddContactFormLicensing()`) and `Composers/ContactFormComposer.cs`. Calling `AddContactForm()` from the composer and from `Program.cs` registers each service once.

Change these in your copy:

- The product ID in `ContactFormProduct`.
- The public key in `ContactFormProduct`. Use your own, never the demo key.
- The feature names, and the checks that use them in `ContactFormLicensing`.

`ContactFormLicensing` needs `ISubmissionStore` (for the monthly count) and the request host. Keep the interface and replace only `InMemorySubmissionStore`.

`Form/` is the public form: a view component, its view model, a surface controller and the handler it delegates to. The view model has `ShowUploads` only, so nothing else about the license reaches the page. Submissions are recorded whatever the license state; the file is read (name and size only) only when uploads are shown for that request. The view is `Views/Shared/Components/ContactForm/Default.cshtml`, compiled into the package.

`Submissions/` is an in-memory stand-in for real storage behind `ISubmissionStore`. Replace it. `Demo/` is described next.

### Hidden submissions

A submission the license does not cover is still recorded, but the Submissions screen hides its details. A license that is not `Valid` hides every submission this month. A `Valid` license with a monthly limit of N hides the (N+1)th submission onwards, in the order they arrived; the first N stay visible. The domain list does not hide anything: a host the license does not name shows the banner only.

An editor and an administrator see the same thing, because both read the one `submissions` endpoint. A hidden row shows the email with all but the first character of each part replaced by `*` (`carl@sargunar.com` becomes `c***@s*******.c**`) and the note "Details hidden until the license covers this submission." The name, message, date and upload are not in the response at all, so they cannot be read from the browser's devtools. The masked email is the only part of a hidden submission that leaves the server.

Nothing is lost. The store keeps every submission in full and hiding only changes what the endpoint returns. Fix the license and the next request shows this month's submissions in full. Over the limit, a new month starts the count again for new submissions; the screen lists only the current month.

A real vendor should weigh this against the site owner's interests. The site owner's own enquiries are in those submissions, and hiding them can cost the owner real customers. This sample hides them to show a license state having a visible effect; a real product may prefer to show everything and warn.

## Controllers/

The package's back-office API: four endpoints in one OpenAPI document, `acme-contact-form`. In the demo site (Development environment) it is served at `https://localhost:44365/umbraco/swagger/acme-contact-form/swagger.json`. Every endpoint needs a signed-in back-office user. With none, each answers 401 (checked by hand against the running site, not by a test). The path prefix is `/umbraco/acme-contact-form/api/v1/`.

| Endpoint | Policy | Returns |
|---|---|---|
| `GET license/status` | Settings section access | `AdminLicenseStatus`: the dashboard's data for the request host. |
| `GET submissions` | Content section access | This month's submissions (some hidden, see below) and the editor banner, or no banner when nothing is due. |
| `GET demo/entries` | Settings section access | The demo picker's list and the selection. Demo only; 404 when the demo is off. |
| `POST demo/select` | Settings section access | 204 once chosen, 400 for an unknown entry. Demo only; 404 when the demo is off. |

To call an endpoint as a given back-office user, open `https://localhost:44365/umbraco/swagger`, pick "Acme Contact Form Backoffice API" (the `acme-contact-form` document) in the document selector, click Authorize and sign in as that user. The page uses the back-office OAuth client `umbraco-swagger`; try-it-out is off by default, so click "Try it out" on an endpoint first. Swagger UI is served in the demo site (Development environment). The dashboards make the same calls, so the browser's devtools Network tab shows them while you use the back office.

Umbraco's default Editors group (seeded in this site's database) has the Content and Media sections but not Settings. So an editor can read `submissions` but is refused by `license/status` and the demo endpoints; use an administrator, or a group with Settings access, to see the licensing dashboard.

The policy is on each action, never on the class. A class-level `[Authorize]` combines with each action's own, so a user admitted by an action alone (a Content-only editor reading submissions) would be refused by the class policy as well. A test checks each action carries exactly its own policy.

## Client/

The back-office client: Lit, Vite and TypeScript, from the Umbraco 17 template. `npm run build` in `Acme.ContactForm/Client` builds it into the package's `wwwroot/App_Plugins/AcmeContactForm`; `run-demo.mjs` does this when needed. It needs Node 24.13 or newer.

Two dashboards, each fetching on every open:

- The licensing dashboard, in Settings: `src/dashboards/license-dashboard.element.ts`.
- The submissions dashboard with the editor banner, in Content: `src/dashboards/submissions-dashboard.element.ts`.

All license wording comes from the server. The client lays it out and adds only its own labels, the tags "unverified", "covered" and "not covered", and the message each dashboard shows when its data cannot be loaded. The demo picker adds its heading, a notice naming the chosen entry, the "Demo date:" label and fallback error messages for when the server gives none.

The licensing dashboard has two add-on points:

- An `<umb-extension-slot>` for extension type `acmeContactFormLicensePanel`. Any extension of that type is shown in the dashboard.
- The `window` event `acme-contact-form-license-changed`. Dispatch it and the dashboard reloads.

The demo picker (`src/demo/demo-picker.element.ts`) uses both. Nothing imports it.

`src/bundle.manifests.ts` loads `src/demo/manifest.ts` through `import.meta.glob`. With the folder deleted the glob finds nothing, so the client still builds.

To regenerate the API client:

1. Start the site: `dotnet run --project samples/Acme.ContactForm.Site --launch-profile https`.
2. In `Acme.ContactForm/Client`, run `npm run generate-client`.

It reads `https://localhost:44365/umbraco/swagger/acme-contact-form/swagger.json` and writes `src/api/`, which is committed. Regenerate after any controller or response change. Generated calls throw on an error response unless called with `throwOnError: false`; the picker does this to read the 404 and 400 answers.

## Demo/: delete when copying

`Demo/` exists for the demo site only. To remove it, delete the `Demo/` folder and `Client/src/demo/`. No other file needs an edit: the package builds and runs without it.

What is in it:

- `demo-keys.json` and its reader (`DemoKeyEntry`, `DemoKeys`): the committed demo key set, embedded in the package.
- `DemoKeySelection`: the entry the picker chose, or none. Held in memory only.
- `DemoKeySource`: wraps the configured key source. While an entry is chosen it supplies that entry's key, and the key source name reads `Demo selection: <entry>`.
- `DemoClock`: the chosen entry's demo date when it has one (only "Valid: expiring soon" does), the real clock otherwise. It is given to the product only and is never registered as the container's `TimeProvider`, so the monthly submission count always uses the real clock.
- `DemoController`, `ContactFormDemoServiceCollectionExtensions` (`AddContactFormDemo()`) and `ContactFormDemoComposer`: the `demo/entries` and `demo/select` endpoints, the registration, and the composer that runs it. `AddContactFormDemo()` calls `AddContactFormLicensing()` itself before it replaces the product and licensing, so it works whatever order the composers run in. The picker element is in `Client/src/demo/`, loaded through its own manifest (see Client/).

It is off unless `ContactForm:Demo:Enabled` is true, read once at start-up. With it off nothing in `Demo/` is registered and both demo endpoints answer 404. The demo site's committed `appsettings.json` turns it on. To turn it off for one run without changing a tracked file, set the environment variable `ContactForm__Demo__Enabled=false`: `ContactForm__Demo__Enabled=false node samples/run-demo.mjs` in a POSIX shell, or `$env:ContactForm__Demo__Enabled="false"` then `node samples/run-demo.mjs` in PowerShell (the variable stays set for that terminal session; clear it with `Remove-Item Env:ContactForm__Demo__Enabled`). Both endpoints need Settings section access.

The picker never writes settings: the choice lives in memory and a restart goes back to the configured key. Choosing "configured" in the same request body (`{ "entry": "configured" }`) also goes back to it. An unknown entry name answers 400 and changes nothing.

Expect log noise in a demo session: each choice changes the licensing condition, so the state log writes Warning and Error lines on purpose (for example when you choose Expired or Damaged key). That is the logging working, not a fault.

`license/status` returns `AdminLicenseStatus` whether or not the demo is on; while an entry is chosen it shows in `KeySourceName` (`Demo selection: <entry>`). The chosen entry and its demo date come from `demo/entries`. Nothing outside `Demo/` refers to the demo services; the `ContactForm:Demo` setting is the one mention, in `ContactFormOptions`, and is harmless to leave.

`Licensing/` itself holds no demo code: `ContactFormProduct.Clock` is the one clock the evaluator and the expiring-soon check share.
